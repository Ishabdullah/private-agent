### 2026-08-16 — Phase 5b crash fix: toggling "Voice Assistant (Beta)" crashed the app and wouldn't reopen

**User report**: turning on the Settings → Voice Assistant (Beta) → "Background listening" toggle crashed the app, and it wouldn't open again afterward.

**Root cause (found by code review, not logcat — see note below on why)**: `settings_screen.dart`'s new toggle called `VoiceAssistantForegroundService.start()` directly with no runtime microphone-permission check first. On Android 14+ (API 34+), calling `startForeground()` with `FOREGROUND_SERVICE_TYPE_MICROPHONE` without `RECORD_AUDIO` already granted throws a `SecurityException` — and since `onStartCommand` returned `START_STICKY`, Android would keep relaunching (and re-crashing) the service every time it died, which is consistent with "wouldn't open up again" (a crash loop, not a one-off crash).

**This environment could not pull the actual crash stack trace to confirm it.** This Termux install is on the same physical device the user tested on (confirmed `logcat` binary exists and runs), but Android sandboxes `logcat` to an app's own process logs for non-root, non-shell callers — `logcat -d` only showed Termux's own log lines, nothing from `com.orailnoor.privateagent`, and the crash buffer (`-b crash`) and events buffer were both empty/inaccessible. **If this happens again, the fastest way to get a real stack trace is `adb logcat` from a PC with the phone connected (USB debugging), or a third-party on-device log viewer app with read-logs access** — worth setting up before the next round of native-code changes, since this class of bug is exactly what happens when adding new native code and doesn't reliably reproduce as builds change.

**Fixes applied** (defense in depth — several because we couldn't confirm which exact one fired) to `VoiceAssistantForegroundService.kt` and `settings_screen.dart`:
1. **`settings_screen.dart`**: the toggle now calls `Permission.microphone.request()` and shows a SnackBar + aborts if not granted, before ever calling `VoiceAssistantForegroundService.start()`. This is very likely the actual fix, but see #2-4 for what makes this robust against being wrong.
2. **`onStartCommand` no longer returns `START_STICKY`, always `START_NOT_STICKY`** — this is the fix for the "wouldn't reopen" half specifically. The service is only ever meant to run when Dart explicitly starts/resumes it; letting Android auto-restart it after any kind of failure turns a single crash into an infinite loop. This alone would have prevented the "app wouldn't open again" symptom even if the underlying permission issue weren't fixed.
3. **`startListening()`** now explicitly checks `RECORD_AUDIO` via `ContextCompat.checkSelfPermission` before calling `startForeground(..., FOREGROUND_SERVICE_TYPE_MICROPHONE)` and calls `stopSelf()` instead if it's not granted (native-side defense, in case anything else ever calls `start()` without going through the Settings toggle's check).
4. **Broadened `catch (e: Exception)` to `catch (e: Throwable)`** in `startListening()`, `startSpotting()`, and added a new try/catch around the `processSamples()` decode loop. `UnsatisfiedLinkError` (thrown if the sherpa-onnx native `.so` is missing/mismatched for the device's ABI) is a `LinkageError`/`Error`, not an `Exception` — the original code would NOT have caught it, so any ABI/native-library problem would have crashed the whole process past all the try/catch blocks that were there. (True native SIGSEGV/abort() inside the `.so` itself still can't be caught by any JVM-level catch — that class of failure is unfixable from Kotlin and would need to be ruled out via the model/library itself if it recurs.)
- **One self-introduced lint** (`use_build_context_synchronously` on the new permission-check SnackBar, using `context` after an `await` guarded only by the State's `mounted` rather than `context.mounted`) — fixed and reverified (114 issues, same pre-existing baseline as every other session).
- **Verified via colab-cli** (fresh session `privateagent-crashfix`): `flutter pub get`/`test` (42/42)/`analyze` (114, no new issues after the lint fix) clean, `flutter build apk --debug --split-per-abi` succeeded. Downloaded arm64-v8a build (163 MB) to `~/storage/downloads/privateagent-crashfix-arm64-debug.apk`.
- **What to test**: uninstall the previous build first (clears any stuck service state from the crash loop), install this one, go to Settings → Voice Assistant (Beta), toggle "Background listening" on. It should now either (a) work — grant mic permission if prompted, see the ongoing notification, no crash — or (b) show a clear SnackBar asking for microphone permission instead of crashing, if permission was somehow denied. If it still crashes, that's a different bug than the one fixed here and we'll need an actual stack trace next time (see the logcat-access note above) rather than another round of defensive guessing.
- **Next concrete action**: unchanged — Phase 6, or real-device validation of Phase 5 as a whole, once this fix is confirmed to actually resolve the crash.

### 2026-08-16 — Real root cause found: the permission fix wasn't it. The int8 KWS model crashed the ONNX runtime deterministically

**It crashed again after installing the "fixed" build above.** User set up `adb` over WiFi and gave permission to use it directly — this changed everything about how debuggable this class of bug is going forward, and should be the default troubleshooting path from now on for any crash that isn't reproducible from code review alone.

**What `adb logcat` actually showed** (the previous session's fixes were real but treating the wrong cause): every crash was `Fatal signal 6 (SIGABRT)` with an identical abort message, byte-for-byte, every single time:
```
terminating due to uncaught exception of type Ort::Exception: Non-zero status code returned while running Reshape node. Name:'/downsample/Reshape_1' Status Message: .../reshape_helper.h:57 onnxruntime::ReshapeHelper::ReshapeHelper(...) input_shape_size == requested_shape_size was false. The input tensor cannot be reshaped to the requested shape. Input shape:{17,1,128}, requested shape:{8,2,1,128}
```
This is a **native C++ exception inside onnxruntime**, thrown from deep inside the sherpa-onnx JNI layer with no Java/Kotlin-catchable equivalent — it calls `std::terminate()` → `abort()`, which no `try/catch` in Kotlin (not even `catch (e: Throwable)`, which was added last session for a different, real-but-not-applicable-here reason) can intercept. **The previous session's permission-check and `START_STICKY`→`START_NOT_STICKY` fixes were correct and worth keeping** (confirmed via this session's adb testing: triggering the service without `RECORD_AUDIO` now fails cleanly with a caught `SecurityException` and a log line, no crash) — they just weren't the cause of *this* crash. The crash was 100% deterministic and immediate (within ~20 seconds of the KWS loop starting, same every time, no dependency on what was said or not said), which is the signature of a model/runtime incompatibility, not a usage bug or a race condition.

**Root cause**: the bundled `sherpa-onnx-kws-zipformer-gigaspeech-3.3M-2024-01-01-**mobile**` model (specifically its **int8-quantized** encoder+joiner) is incompatible with the sherpa-onnx **1.13.5** runtime's streaming Zipformer2 decode path on this device. The reshape math (`17,1,128` → `8,2,1,128`, i.e. trying to split a 17-frame tensor into pairs of 8) suggests an off-by-one in the encoder's internal chunk/cache-state handling that only manifests with the quantized export — the model was published March 2024, the runtime library is a mid-2026 release, and JitPack's AAR publishing for this repo didn't even exist until December 2024 (`sherpa-onnx.aar` support landed in commit `4dc4f1a7`, first available starting `v1.10.35`) — so there was never a way to pin a "contemporaneous" library version via JitPack; the oldest available AAR already postdates this model by ~9 months.

**Fix**: swapped from the int8-quantized `encoder.int8.onnx`/`joiner.int8.onnx` to the **full-precision** `encoder.onnx`/`joiner.onnx` from the same model release (`sherpa-onnx-kws-zipformer-gigaspeech-3.3M-2024-01-01.tar.bz2`, the non-`-mobile` tarball) — `decoder.onnx` was already full-precision in both bundles, unchanged. `assets/kws/` bundle grew from ~5.3 MB to **~14 MB** (still small). Updated `VoiceAssistantForegroundService.loadKeywordSpotter()`'s asset paths (`encoder.int8.onnx`→`encoder.onnx`, `joiner.int8.onnx`→`joiner.onnx`) and `assets/kws/NOTICE.md` to document why the int8 variant is deliberately not used.

**Verified for real on the user's physical device** (Samsung, `samsung/e3qsqw/e3q:16`, API 36) via `adb` over WiFi — this is the first Phase 5 change actually confirmed on hardware, not just Colab-built:

### 2026-08-16 — Second real crash: SIGSEGV on actual wake-word detection (fixed, device-verified end to end)

**The fp32 model fix above was necessary but not sufficient.** User reported: saying "Hey [name]" now beeped (mic engaged) but then the app crashed with Android's "app has a bug" system dialog. This is a *different* crash from the reshape one — it only happens on an actual detection firing, not just from the KWS loop running.

**Root cause, found immediately via the now-standard adb logcat workflow**:
```
VoiceAssistant: Wake word detected for NOVA
libc: Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x8 in tid ... (Thread-6)
...VoiceAssistantForegroundService.processSamples+824
```
`onWakeWordDetected()` called `stopSpotting()` — but it was itself called from *inside* `processSamples()`'s decode loop, which runs *on* `recordingThread`. `stopSpotting()` did `recordingThread?.join(500)` (a thread trying to join itself — meaningless) and, worse, called `stream.release()` (freeing the native `OnlineStream`) while the surrounding `while (spotter.isReady(activeStream))` loop in `processSamples()` still held and was about to reuse that same `activeStream` reference — a use-after-free. `fault addr 0x8` (a near-null read) is the classic signature of exactly this kind of freed-object dereference. No `catch (e: Throwable)` can intercept this either — it's a native SIGSEGV, not a JVM exception.

**Fix** (`VoiceAssistantForegroundService.kt`): restructured so native resource cleanup only ever happens once, in `processSamples()`'s own `finally` block, on the thread that actually owns the resources:
- Detecting a keyword now just sets `isSpotting = false`, calls a renamed `notifyWakeWordDetected()` (launch-activity logic only, no cleanup), and `break`s out of both loops via a labeled `loop@`.
- `processSamples()` wraps its whole loop in `try { ... } finally { releaseAudioResources() }` — this runs whether the loop exits via detection, an exception, or `isSpotting` being flipped externally.
- `stopSpotting()` (still used for `ACTION_STOP` / `onDestroy` / setup failures — all external-thread callers) now just flips the flag, joins the thread from *outside* it (valid this time), and calls the same `releaseAudioResources()` afterward as a safety net for the setup-failure case where the thread never started.

### 2026-08-19 — Cross-cutting bug found during Phase 6-8 device testing: models emitting `<tool_call>` tags instead of JSON silently did nothing

While the user was working through the real-device validation backlog for Phases 6-8 (triggered via voice: "what's the weather today and what's the time", then "text Mom I love you"), the currently-configured model responded with its own baked-in `<tool_call>action_name<arg_key>k</arg_key><arg_value>v</arg_value></tool_call>` tool-calling syntax instead of the JSON format `AiService`'s system prompt asks for. `AiService.parseAction` only recognized the JSON shape, so these responses fell through as plain conversational text — the raw tags got displayed/spoken literally and the action (`read_screen`, `send_sms`) never actually executed. This is a known failure mode for instruction-tuned models with strong baked-in tool-calling fine-tunes, especially when the request doesn't use the API's native `tools`/`tool_choice` parameter (this app calls a raw chat-completions endpoint, so the model falls back to whatever it was trained on when the system-prompt-only instruction doesn't stick).

**Fix**: `parseAction` now falls back to a `_parseToolCallTagAction` parser that converts the tag format into the same `AgentAction` shape (narration before the tag becomes `action.response`; numeric-looking `arg_value`s are coerced to `num` so downstream `as num?` casts in `set_alarm`/`set_volume`/`set_brightness` don't crash on a String). Also tightened the system prompt with an explicit "do NOT invent your own tool-calling syntax" instruction to reduce recurrence. Added `test/ai_service_parse_action_test.dart` coverage (3 new cases: no-params tag, tag with params + narration, numeric coercion). Verified via colab-cli: 68/68 tests passing (up from 65), no new analyze issues, debug APK built and installed via `adb install` so testing could resume immediately. ### 2026-08-19 — Two more real bugs found continuing the Phase 6-8 device validation pass, after the tool_call-tag fix

User reported the tool_call fix didn't fully resolve things: voice-triggered actions still just narrated what they'd do instead of executing, and the destructive-action confirmation prompt cut off the mic before the user could say yes/no.

**Bug A — voice turns never emit action JSON at all** (a different failure mode than the tag issue): `AiService.sendMessageStream` appends `_voiceResponseStyleHint` ("write plain spoken sentences only") to the end of the system prompt for every voice-originated turn. Sitting after and unqualified relative to the JSON-action instructions earlier in the prompt, this reads as a direct conflict, and the model reasonably prioritized the more recent "plain spoken sentences" instruction over "respond with ONLY JSON" — so voice-triggered action requests got pure narrated prose with no structured output whatsoever (not JSON, not even a `<tool_call>` tag). **Fix**: reworded the hint to explicitly say it governs wording only (the JSON's `response` field, or plain-text conversational replies) and does not change whether JSON is used for actions.

**Bug B — confirmation/follow-up mic capture starts before TTS finishes speaking**: `VoiceService` never called `_tts.awaitSpeakCompletion(true)`, so `await voiceService.speak(...)` (flutter_tts's default behavior) resolves as soon as playback *starts*, not when it *finishes*. Every caller that starts listening right after an `await speak(...)` — the destructive-action confirmation prompt, and the follow-up-question re-listen — was therefore starting the mic while the prompt was still being read aloud; the `confirmation` listen mode's short silence-based cutoff then ended the capture before the user had a chance to actually respond, matching the reported symptom exactly. **Fix**: call `_tts.awaitSpeakCompletion(true)` once during `VoiceService.init()`.

**Root cause, found by re-reading `AssistantInteractionSession.kt` against the AOSP `VoiceInteractionSession` docs already fetched during the original Phase 9 session** (this is exactly the kind of bug an API's own documented lifecycle predicts — not something that needed new research): `onShow()` called `startVoiceActivity(intent)` immediately followed by `hide()`. `startVoiceActivity` is **asynchronous** — it requests the activity start from the system server and returns immediately, well before the activity actually exists on screen. Calling `hide()` right after tears the session down before `MainActivity` ever gets a chance to display, which is consistent byte-for-byte with "nothing happens." The user's instinct that "a special screen" was missing was correct in spirit: the *session's own content view* (the plain "PrivateAgent is listening..." `TextView` from `onCreateContentView()`) is that special screen — exactly what other assistants show — but it was being destroyed before it could ever be seen, and the destruction likely also interfered with the started activity's own attach sequence.

**Fix**: moved the `hide()` call out of `onShow()` and into a new `onTaskStarted(intent, taskId)` override — this is a real `VoiceInteractionSession` lifecycle callback, documented as firing "when a task initiated by startVoiceActivity has actually started," i.e. exactly the right signal to know it's now safe to dismiss the session UI. Also added a defensive 4-second fallback (`Handler.postDelayed`) that calls `hide()` regardless if `onTaskStarted` never fires for some OEM-specific reason (Samsung/OneUI's assistant-role plumbing is already flagged as unreliable in plan doc Section 10.2, and this user is on a Samsung device) — a safety net, not the primary mechanism, cancelled via `onHide()` if the real callback does fire first.

### 2026-08-19 — Phase 9 device-reported bug #2: manifest missing voice intent-filter (SecurityException), then a second real bug (fallback timer closing the whole app), both found live via adb logcat

**User report #1**: after installing the fix above, selecting PrivateAgent as assistant and pressing the side button now visibly flashed a screen (matching what other assistants show) but then crashed. **User had proactively turned on adb-over-WiFi** specifically so real crash logs could be pulled — this made both bugs in this session trivial to root-cause instead of guessing.

**Bug A — `SecurityException: Starting under voice control not allowed for`**: `adb logcat` showed a clean Java stack trace immediately: `Instrumentation.checkStartActivityResult` → `VoiceInteractionSession.startVoiceActivity` → `AssistantInteractionSession.onShow`. Traced the exact AOSP condition by reading `ActivityStarter.java` directly (via `android.googlesource.com/.../ActivityStarter.java?format=TEXT`, base64-decoded): when `startVoiceActivity` is starting a **new** voice session (our case), `ActivityStarter.executeRequest` calls `PackageManager.activitySupportsIntentAsUser(intent.getComponent(), intent, ...)` and fails the whole start with `START_NOT_VOICE_COMPATIBLE` unless the **target activity's manifest declares an `<intent-filter>` matching the intent** — including `CATEGORY_VOICE`, which `startVoiceActivity` always adds automatically — even though the intent is already explicit (named by component). This is a real, intentional platform restriction, not a workaround-able bug: an activity must opt in to being started this way. `MainActivity`'s only existing `<intent-filter>` was the `MAIN`/`LAUNCHER` one, which doesn't match. **Fix**: added a second `<intent-filter>` to `MainActivity` matching `action=com.orailnoor.privateagent.action.ASSISTANT_INTERACTION` + `category=android.intent.category.VOICE`. **Repeated the exact same `--` inside an XML comment mistake from the previous manifest edit** while writing the explanatory comment for this fix — caught and fixed before building this time by grepping the whole file for stray `--` outside `<!--`/`-->` delimiters first.

**User report #2** (after installing the intent-filter fix): "the first time i used the side button the app screen for private agent came up but closed the app[;] the second time it worked normally." **Logcat told a different story than the user's read of it** — both the first (12:28:01) and second (12:30:31) invocations closed automatically at almost exactly +4.0s after opening (12:28:05.537 and 12:30:35.212 respectively), with **zero exceptions or crashes anywhere in the log** — Flutter had fully rendered, `speech_to_text` had even started listening, before the task was torn down by a normal (non-error) `CLOSE` transition. The 4-second timing was an exact match for `AssistantInteractionSession`'s own fallback timer (`FALLBACK_HIDE_DELAY_MS = 4000L`, added in the previous session as a defensive safety net in case `onTaskStarted` never fired). Root cause: `onTaskStarted` was in fact never firing on this device within that window, so the fallback fired instead — and calling `hide()` on the session while its launched task was still the active `IS_VOICE_INTERACTION` task **closed the entire launched task**, not just the session's small overlay view (an undocumented side effect, at least undocumented anywhere surfaced during this investigation). This is a clean example of a "defensive" addition causing the exact class of bug it was meant to guard against, once the assumption behind it (that `hide()` is always a safe no-op on the launched activity) turned out to be wrong on this device.

**Fix (v3, current)**: removed `onTaskStarted`'s manual `hide()` and the fallback timer entirely — `AssistantInteractionSession` now only calls `startVoiceActivity()` in `onShow()` and does nothing else. Relies entirely on `VoiceInteractionSession`'s own base-class default `onTaskFinished` implementation (already calls `hide()`, per AOSP source read during the original Phase 9 session), which only fires when the *user* actually finishes the last activity of the launched task — i.e. closes/backs out of PrivateAgent — the correct, already-built-in trigger. No custom timing logic left in this class at all.
